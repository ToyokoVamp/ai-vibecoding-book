# 1.12 — Domain Model, Entity, Value Object и Aggregate

## Domain Model (доменная модель)

**Domain Model (доменная модель)** — программное представление важных бизнес-понятий и правил предметной области.

Для SEO-системы это могут быть:

```text
Site (сайт)
SearchQuery (поисковый запрос)
Position (позиция)
SEOIssue (SEO-проблема)
Recommendation (рекомендация)
Analysis (анализ)
```

Это уже не просто `string`, `integer` или `dictionary`, а объекты с предметным смыслом.

## Entity (сущность)

**Entity (сущность)** — объект, у которого важна собственная identity (идентичность).

Например:

```text
Site (сайт)
id = 42
domain = novaplastic.ru
```

Позже домен может измениться, но `id = 42` означает, что это та же сущность.

Пример:

```text
User (пользователь)
id = 123
email = old@example.com
```

После изменения email это всё ещё тот же пользователь.

## Value Object (объект-значение)

**Value Object (объект-значение)** определяется своими значениями, а не отдельной identity (идентичностью).

Пример:

```text
Money (деньги)
amount = 100
currency = EUR
```

Два объекта `Money(100, EUR)` по смыслу эквивалентны.

Ещё пример:

```text
DateRange (диапазон дат)
start = 2026-10-01
end = 2026-10-31
```

Для Value Object (объекта-значения) обычно полезна immutability (неизменяемость): вместо изменения старого значения создаётся новое.

## Entity против Value Object

Проверка:

> Если все значения совпадают, считаем ли мы два объекта одним и тем же?

Если да — это кандидат на **Value Object (объект-значение)**.

Если важна отдельная история и identity (идентичность) — это **Entity (сущность)**.

Например:

```text
Position (позиция)
→ Value Object (объект-значение)

RankingMeasurement (измерение позиции)
→ Entity (сущность), если у записи есть собственная история и идентичность
```

## Aggregate (агрегат)

**Aggregate (агрегат)** — группа связанных domain objects (доменных объектов), которые должны сохранять общие business invariants (бизнес-инварианты).

Пример заказа:

```text
┌──────────── Aggregate (агрегат) ────────────┐
│                                             │
│       Order (заказ)                         │
│       Aggregate Root (корень агрегата)      │
│              │                              │
│      ┌───────┼────────┐                     │
│      ↓       ↓        ↓                     │
│ Item      Item     Address                   │
│ товар     товар    адрес                     │
│                                             │
└─────────────────────────────────────────────┘
```

## Aggregate Root (корень агрегата)

**Aggregate Root (корень агрегата)** — главный объект агрегата, через который внешний код изменяет его состояние.

Например правило:

```text
ClosedOrder (закрытый заказ)
не может получить новый OrderItem (товар заказа)
```

Вместо произвольного изменения внутренних объектов вызывается поведение `Order (заказ)`, которое проверяет правило.

## Invariant (инвариант)

**Invariant (инвариант)** — правило, которое должно всегда оставаться истинным.

Примеры:

```text
Order.total >= 0
```

```text
SubscriptionEnd >= SubscriptionStart
```

В SEO-системе `Analysis (анализ)` может быть кандидатом на Aggregate Root (корень агрегата), если он контролирует правила своего состояния:

```text
Analysis (анализ)
├── Site (сайт)
├── Period (период)
├── Metrics (метрики)
├── Issues (проблемы)
└── Status (статус)
```

Например анализ нельзя перевести в `completed (завершён)`, пока не рассчитаны обязательные метрики.

> [!IMPORTANT]
> ## Ключевые идеи — обязательно запомнить
>
> - **Domain Model (доменная модель)** — представление бизнес-понятий и правил в коде.
> - **Entity (сущность)** — объект, у которого важна identity (идентичность).
> - **Value Object (объект-значение)** — объект, который определяется своими значениями.
> - **Aggregate (агрегат)** — граница согласованности для связанных доменных объектов и правил.
> - **Aggregate Root (корень агрегата)** — объект, через который внешний код изменяет агрегат.
> - **Invariant (инвариант)** — правило, которое должно всегда сохраняться.

# 1.13 — Domain Service, Application Service и Repository

## Domain Service (доменный сервис)

**Domain Service (доменный сервис)** содержит бизнес-логику, которая не принадлежит естественно одной конкретной Entity (сущности) или Value Object (объекту-значению).

Например:

```text
SEOIssueEvaluator (оценщик SEO-проблем)
```

может определять severity (критичность) проблемы на основе нескольких объектов:

```text
Site (сайт)
SearchMetrics (поисковые метрики)
HistoricalMetrics (исторические метрики)
RankingTrend (динамика позиций)
```

Domain Service (доменный сервис) остаётся частью business logic (бизнес-логики) и не должен смешиваться с HTTP, SQL, Telegram API и другими инфраструктурными деталями.

## Application Service (сервис приложения)

**Application Service (сервис приложения)** координирует выполнение Use Case (сценария использования).

Например `RunAnalysisService (сервис запуска анализа)` может:

```text
1. загрузить Site (сайт)
2. получить Metrics (метрики)
3. вызвать Analytics (аналитику)
4. применить Rules (правила)
5. сохранить Analysis (анализ)
6. опубликовать AnalysisCompleted Event (событие завершения анализа)
```

Главное различие:

```text
Domain Service (доменный сервис)
= бизнес-правило

Application Service (сервис приложения)
= orchestration (оркестрация) сценария
```

Application Service (сервис приложения) должен быть скорее дирижёром, а не местом, где вручную реализована вся предметная логика.

## Repository (репозиторий)

**Repository (репозиторий)** — абстракция доступа к данным доменной модели.

Вместо:

```sql
SELECT * FROM sites WHERE id = 42;
```

высокоуровневый код может использовать:

```text
SiteRepository.get_by_id(42)
```

Схема:

```text
Application / Domain Logic (логика приложения / доменная логика)
↓
SiteRepository Contract (контракт репозитория сайтов)
↑
PostgresSiteRepository (реализация репозитория для PostgreSQL)
```

Это продолжение Dependency Inversion Principle (принципа инверсии зависимостей): важная логика зависит от контракта, а не от конкретной БД.

## Repository и DAO

**DAO — Data Access Object (объект доступа к данным)** обычно ориентирован на записи и таблицы.

**Repository (репозиторий)** старается говорить языком domain (предметной области) и возвращать domain objects (доменные объекты).

Упрощённо:

```text
DAO
→ get_row_by_id()

Repository (репозиторий)
→ get_site(site_id)
```

## Полная цепочка

```text
HTTP Controller (HTTP-контроллер)
↓
RunAnalysisService (сервис запуска анализа)
↓
SiteRepository (репозиторий сайтов)
↓
Collector (сборщик данных)
↓
Analytics (аналитика)
↓
SEOIssueEvaluator (оценщик SEO-проблем)
↓
AnalysisRepository (репозиторий анализов)
↓
Event (событие)
```

> [!IMPORTANT]
> ## Ключевые идеи — обязательно запомнить
>
> - **Domain Service (доменный сервис)** содержит бизнес-логику, которая не принадлежит естественно одной Entity (сущности).
> - **Application Service (сервис приложения)** координирует Use Case (сценарий использования).
> - **Repository (репозиторий)** скрывает детали хранения и предоставляет domain objects (доменные объекты).
> - Repository Pattern (паттерн репозитория) не имеет отношения к Git Repository (Git-репозиторию), кроме совпадения слова.

# 1.14 — Use Case, Command, Query и CQRS basics

## Use Case (сценарий использования)

**Use Case (сценарий использования)** — конкретная цель пользователя или системы.

Примеры:

```text
Run SEO Analysis (запустить SEO-анализ)
Generate Report (сформировать отчёт)
Connect Site (подключить сайт)
Invite User (пригласить пользователя)
Get Analysis History (получить историю анализов)
```

## Command (команда)

**Command (команда)** просит систему изменить состояние.

Примеры:

```text
CreateAnalysis (создать анализ)
ConnectSite (подключить сайт)
DeleteUser (удалить пользователя)
ChangeSubscriptionPlan (изменить тариф)
```

## Query (запрос на чтение)

**Query (запрос на чтение)** получает данные и не должен неожиданно изменять состояние системы.

Примеры:

```text
GetSite (получить сайт)
GetAnalysisHistory (получить историю анализов)
GetCurrentPosition (получить текущую позицию)
ListSEOIssues (получить список SEO-проблем)
```

Простая разница:

```text
Command (команда)
→ изменить состояние

Query (запрос на чтение)
→ получить данные
```

## Side Effect (побочный эффект)

**Side Effect (побочный эффект)** — изменение чего-либо вне локального результата функции.

Примеры:

```text
запись в БД
отправка email
изменение файла
HTTP-запрос
публикация события
```

Query (запрос на чтение) желательно не наделять неожиданными side effects (побочными эффектами).

## CQS — Command Query Separation

**CQS — Command Query Separation (разделение команд и запросов)** — принцип, согласно которому операция по возможности либо изменяет состояние, либо читает данные.

```text
Command (команда)
→ изменить

Query (запрос)
→ прочитать
```

## CQRS — Command Query Responsibility Segregation

**CQRS — Command Query Responsibility Segregation (разделение ответственности команд и запросов)** — более архитектурный подход, в котором операции изменения и чтения могут использовать разные модели, обработчики и при необходимости разные хранилища.

В простом modular monolith (модульном монолите) это может быть всего лишь:

```text
application/
├── commands/ (команды)
└── queries/  (запросы)
```

Без Kafka, отдельных баз и микросервисов.

## Command Handler и Query Handler

```text
RunAnalysisCommand (команда запуска анализа)
↓
RunAnalysisHandler (обработчик команды запуска анализа)
```

```text
GetAnalysisHistoryQuery (запрос истории анализов)
↓
GetAnalysisHistoryHandler (обработчик запроса истории анализов)
```

Handler (обработчик) часто является конкретной формой Application Service (сервиса приложения).

## DTO — Data Transfer Object

**DTO — Data Transfer Object (объект передачи данных)** — простой объект для передачи данных между слоями или наружу через API.

Например:

```text
AnalysisSummaryDTO (DTO краткого анализа)
├── id
├── site_domain
├── created_at
├── issues_count
└── status
```

DTO не обязан быть Entity (сущностью).

## Read Model и Write Model

**Read Model (модель чтения)** оптимизирована для удобного получения данных.

**Write Model (модель записи)** ориентирована на изменение состояния и соблюдение бизнес-правил.

```text
Command (команда)
↓
Write Model (модель записи)
↓
Business Rules (бизнес-правила)
```

```text
Query (запрос)
↓
Read Model (модель чтения)
↓
DTO (объект передачи данных)
```

## Command и Event — не одно и то же

```text
Command (команда)
= намерение сделать действие

Event (событие)
= факт, который уже произошёл
```

Например:

```text
RunAnalysis (запустить анализ)
→ Command (команда)

AnalysisCompleted (анализ завершён)
→ Event (событие)
```

> [!IMPORTANT]
> ## Ключевые идеи — обязательно запомнить
>
> - **Use Case (сценарий использования)** — конкретная цель пользователя или системы.
> - **Command (команда)** — изменить состояние.
> - **Query (запрос)** — прочитать данные.
> - **CQS** разделяет изменение и чтение на уровне операций.
> - **CQRS** разделяет ответственность команд и запросов на уровне архитектуры.
> - **Read Model (модель чтения)** может отличаться от **Write Model (модели записи)**.
> - **DTO (объект передачи данных)** — формат передачи данных, а не обязательно доменная сущность.
> - **Event (событие)** сообщает о том, что уже произошло.

# Итог тем 1.12–1.14

```text
Domain Model (доменная модель)
↓
Entity / Value Object / Aggregate
(сущность / объект-значение / агрегат)
↓
Domain Service (доменный сервис)
↓
Application Service (сервис приложения)
↓
Repository (репозиторий)
↓
Command / Query / Event
(команда / запрос / событие)
```

Эти понятия дают более точный язык для проектирования внутреннего устройства модулей, а не только крупных архитектурных блоков системы.
