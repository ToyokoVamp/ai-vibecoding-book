# AI Software Architect — Архитектура, часть 3
## Темы 0.7–0.8

# 0.7 Архитектурные компромиссы: trade-offs

## Цель темы
Понять, почему в архитектуре почти никогда не существует одного «идеального» решения и почему сильный архитектор оценивает последствия каждого выбора.

## Ключевая идея
Хорошая архитектура — не самая сложная, не самая модульная и не самая «правильная по учебнику». Хорошая архитектура соответствует текущей задаче, ограничениям и стадии развития продукта.

## Определение: trade-off
**Trade-off** — компромисс, при котором улучшение одного свойства системы ухудшает другое.

```text
Больше компонентов
↑ изоляция
↓ сложность взаимодействия
```

```text
Больше автоматизации
↑ удобство
↓ контроль
```

```text
Больше кэширования
↑ скорость
↓ актуальность данных
```

## Почему архитектура всегда связана с компромиссами
У проекта всегда есть ограничения:
- время;
- бюджет;
- размер команды;
- опыт разработчиков;
- нагрузка;
- безопасность;
- надёжность;
- скорость выпуска функций.

Нельзя одновременно максимизировать все свойства.

## Две плохие крайности

### Один огромный файл

```text
main.py
└── 5000 строк
```

Внутри:
- сбор данных;
- аналитика;
- правила;
- отчёты;
- ИИ;
- авторизация;
- уведомления.

Проблемы:
- высокая связность;
- тяжёлое тестирование;
- сложно менять код;
- плохо видны ответственности.

### Слишком сложная распределённая система

```text
Frontend
↓
API Gateway
↓
Auth Service
↓
Analytics Service
↓
Rule Service
↓
Report Service
↓
AI Service
↓
Notification Service
↓
Queue
↓
Redis
↓
PostgreSQL
↓
Message Broker
↓
Observability
```

Для маленького MVP такая схема часто избыточна.

Она добавляет:
- сеть;
- конфигурацию;
- таймауты;
- ретраи;
- отдельные логи;
- отдельные деплои;
- больше точек отказа.

## Разумный старт: модульный монолит

```text
seo_app/
├── collectors/
├── analytics/
├── rules/
├── reports/
├── ai/
├── notifications/
└── users/
```

Физически это одно приложение. Логически — несколько областей ответственности.

## Простота vs масштабируемость

### Монолит
Плюсы:
- проще разработка;
- проще тестирование;
- проще деплой;
- меньше инфраструктуры.

Минусы:
- сложнее масштабировать отдельные части независимо;
- при плохих границах может стать хаотичным.

### Микросервисы
Плюсы:
- независимое масштабирование;
- независимые релизы;
- разделение команд;
- можно использовать разные технологии.

Минусы:
- сетевые ошибки;
- больше DevOps;
- сложнее мониторинг;
- сложнее локальная разработка;
- сложнее интеграционные тесты.

## DRY vs понятность
DRY — Don't Repeat Yourself.

Чрезмерное применение DRY может создавать слишком универсальный и трудный код.

Иногда две простые функции лучше одной функции с множеством режимов и параметров.

## Производительность vs читаемость
Обычно приоритет:
1. корректность;
2. понятность;
3. тестируемость;
4. измерение;
5. оптимизация реального узкого места.

Не оптимизируй то, что ещё не стало проблемой.

## Безопасность vs удобство

```text
Чтение данных
→ автоматически

Создание отчёта
→ автоматически

Изменение сайта
→ подтверждение

Удаление данных
→ подтверждение + дополнительная проверка
```

## YAGNI
**YAGNI — You Aren't Gonna Need It.**

Не реализуй заранее функциональность, необходимость которой ещё не подтверждена.

Примеры преждевременного усложнения:
- Kubernetes для нескольких пользователей;
- десятки микросервисов для MVP;
- сложная очередь, когда хватает обычного вызова;
- универсальная plugin-архитектура до появления первого реального плагина.

## Практическое правило архитектора
Перед усложнением системы спроси:

> Какую конкретную проблему решает это усложнение?

Если ответа нет, решение, вероятно, преждевременное.

## Пример на SEO-платформе

### MVP

```text
Frontend
↓
SEO Backend
├── collectors
├── analytics
├── rules
├── reports
└── ai
↓
PostgreSQL
```

### Возможное будущее

```text
API Gateway
├── Core Backend
├── Collector Service
├── Analytics Service
├── AI Service
├── Report Service
└── Notification Service
```

Будущая схема может быть ориентиром, но её не нужно реализовывать в первый день.

## Что нужно запомнить
- идеальной архитектуры не существует;
- архитектура зависит от контекста;
- каждое решение имеет цену;
- сложность не исчезает — она перемещается;
- простота на раннем этапе часто важнее гипотетической масштабируемости;
- не создавай инфраструктуру под проблему, которой ещё нет.

# 0.7.5 Logical, Deployment и Information Architecture

## Цель темы
Научиться смотреть на одну систему с разных архитектурных точек зрения и не смешивать ответственность компонентов, физическое размещение и движение данных.

## Logical Architecture
Описывает логические обязанности системы.

Главный вопрос:

> Какие ответственности существуют?

```text
SEO Platform
├── Collector
├── Analytics
├── Rule Engine
├── AI Advisor
├── Report Generator
├── Notifications
└── Authentication
```

Здесь нет Docker, Kubernetes, серверов или языка программирования.

## Deployment Architecture
Описывает физическое размещение и запуск системы.

Главный вопрос:

> Где и в каком виде работает система?

```text
Ubuntu Server
└── Docker
    ├── Backend Container
    ├── PostgreSQL Container
    └── Redis Container
```

Позже:

```text
Kubernetes Cluster
├── Backend x3
├── Analytics x6
├── AI Worker x4
├── Redis
└── PostgreSQL
```

Логические обязанности могут остаться прежними, а deployment сильно измениться.

## Главное различие

```text
Logical Architecture
→ кто за что отвечает

Deployment Architecture
→ где и как это физически запущено
```

## Information Architecture
В рамках этого курса — взгляд на движение и преобразование данных.

Главный вопрос:

> Как информация проходит через систему?

```text
Яндекс.Метрика
↓
Collector
↓
Normalizer
↓
Storage
↓
Analytics
↓
Rules
↓
AI
↓
Report
```

## Три взгляда на одну систему

### Logical

```text
Collector
Analytics
Rules
AI
Reports
```

### Information

```text
Источник
↓
Collector
↓
Analytics
↓
Rules
↓
Report
```

### Deployment

```text
Server
├── Backend
├── PostgreSQL
└── Redis
```

## Важный принцип
Логическая архитектура обычно должна меняться реже, чем deployment architecture.

## Типичная ошибка
Считать:

```text
Analytics = отдельный контейнер
```

Неверно. Analytics — прежде всего логическая ответственность.

Контейнер — лишь один из вариантов физического запуска.

## Что нужно запомнить
- Logical Architecture: кто за что отвечает;
- Deployment Architecture: где и как это запущено;
- Information Architecture: как движутся данные;
- одна система может иметь несколько архитектурных схем;
- Docker-контейнеры не равны логическим компонентам.

# 0.8 Эволюционная архитектура, масштабируемость и расширяемость

## Цель темы
Понять, как система может расти без необходимости заранее строить её финальную версию.

## Масштабируемость
**Масштабируемость** — способность системы выдерживать увеличение нагрузки.

```text
10 сайтов
↓
100 сайтов
↓
10 000 сайтов
```

```text
1 пользователь
↓
100 пользователей
↓
10 000 пользователей
```

Масштабируемость отвечает на вопрос:

> Что будет, если того же самого станет намного больше?

## Расширяемость
**Расширяемость** — способность системы легко получать новые возможности.

```text
Яндекс.Метрика
Google Search Console
+ Ahrefs
```

```text
Telegram
+ Email
+ Slack
```

## Разница

```text
Масштабируемость
= больше того же самого

Расширяемость
= добавить новую возможность
```

## Эволюционная архитектура
Подход, при котором система развивается по мере появления реальных требований, сохраняя возможность контролируемых изменений.

### Версия 0.1

```text
SEO Backend
├── collectors
├── analytics
├── rules
└── reports
```

### Версия 0.5

```text
SEO Backend
├── collectors
├── analytics
├── rules
├── reports
├── ai
├── users
└── notifications
```

### Версия 2.0

```text
Frontend
↓
Backend
├── analytics
├── rules
├── reports
└── users

Collector Worker
AI Worker
```

### Версия 5.0

```text
API Gateway
├── Core Backend
├── Collector Service
├── Analytics Service
├── AI Service
├── Notification Service
└── Report Service
```

Мы не строим версию 5.0 в первый день. Мы создаём границы, которые позволяют туда прийти при необходимости.

## Принцип

> Сначала отделяй логически. Физически отделяй только тогда, когда появляется реальная причина.

## Точки вариативности
Части системы, которые с высокой вероятностью будут меняться.

```text
Источники данных
├── Yandex
├── Google
└── Ahrefs

LLM
├── OpenAI
├── Claude
└── Ollama

Уведомления
├── Telegram
├── Email
└── Slack

Отчёты
├── Dashboard
├── PDF
└── Excel
```

Именно здесь разумны стабильные контракты и адаптеры.

## Refactoring
**Рефакторинг** — изменение внутренней структуры кода без изменения внешнего поведения.

Было:

```text
analytics.py
```

Стало:

```text
analytics/
├── traffic.py
├── ctr.py
├── positions.py
└── conversions.py
```

## Когда модуль пора выносить в отдельный сервис
Нужна конкретная причина:

- тяжёлая отдельная нагрузка;
- независимое масштабирование;
- влияние на стабильность основного приложения;
- отдельный жизненный цикл релизов;
- отдельная команда;
- другая технология или инфраструктура;
- стабильный контракт с остальной системой.

## Пример: Analytics
Если Analytics замедляет пользовательский API из-за тяжёлых расчётов:

```text
Frontend
↓
Backend API

Analytics Service
├── Worker 1
├── Worker 2
├── Worker 3
└── Worker 4
```

Теперь его можно масштабировать отдельно.

## Типичные ошибки
- пытаться предсказать архитектуру на годы вперёд;
- создавать микросервисы «на будущее»;
- путать рост функциональности с причиной выноса сервиса;
- строить систему под нагрузку, которой ещё нет.

## Что нужно запомнить
- система должна уметь меняться;
- масштабируемость и расширяемость — разные свойства;
- не нужно заранее реализовывать финальную архитектуру;
- логические границы полезно создавать рано;
- физическое разделение должно решать реальную проблему;
- хорошая архитектура делает изменения контролируемыми.
