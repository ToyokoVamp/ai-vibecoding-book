# AI Software Architect — Software Architecture, темы 1.4–1.6

## О чём этот материал

Этот файл продолжает главу **01. Software Architecture** и фиксирует темы:

- **1.4 — Separation of Concerns**
- **1.5 — Encapsulation и Information Hiding**
- **1.6 — Dependency Direction**

Главная идея блока: после того как мы научились видеть модули, coupling и cohesion, нужно научиться правильно разделять обязанности, скрывать внутреннюю реализацию и контролировать направление зависимостей.

---

# 1.4 — Separation of Concerns

## Цель темы

Понять, почему разные типы ответственности нужно отделять друг от друга и как это помогает уменьшать сложность системы.

## Определение

**Separation of Concerns, SoC** — принцип разделения системы на части так, чтобы каждая часть занималась своим типом задач.

`Concern` — отдельная область ответственности системы.

Примеры:

```text
Получение данных
Расчёты
Бизнес-правила
Хранение
Отображение
Уведомления
Авторизация
```

Это разные concerns.

## Плохой пример

```python
def process_site():
    # получить данные из Яндекс API
    # посчитать CTR
    # проверить, низкий ли CTR
    # сохранить результат в PostgreSQL
    # создать PDF
    # отправить Telegram
```

Функция может работать, но внутри смешаны:

```text
API Integration
+
Analytics
+
Rules
+
Storage
+
Reports
+
Notifications
```

Это нарушение Separation of Concerns.

## Разделение по ответственности

```text
Yandex Collector
↓
Analytics
↓
Rule Engine
↓
Storage
↓
Report Generator
↓
Notification
```

Теперь изменения становятся локальнее.

Например:

```text
Telegram → Email
```

должно затронуть Notifications, а не Analytics.

Изменение формулы CTR — Analytics.

Замена способа хранения — Storage.

## Причина и реализация

Важно различать:

```text
Separation of Concerns
→ причина разделения
```

а:

```text
Modules
Components
Layers
Services
→ способы оформить это разделение
```

Сначала архитектор спрашивает:

> Какие ответственности здесь различаются?

А потом:

> Какими границами их оформить?

## Horizontal Separation

Разделение по техническим слоям:

```text
controllers/
services/
repositories/
models/
```

Условно:

```text
Presentation
────────────
Business Logic
────────────
Data Access
```

Это горизонтальный подход.

## Vertical Separation

Разделение по бизнес-возможностям:

```text
analytics/
reports/
notifications/
users/
```

Внутри отдельной области могут находиться её API, логика и доступ к данным.

Например:

```text
analytics/
├── api.py
├── service.py
└── repository.py
```

Это помогает держать связанную бизнес-функцию рядом.

## Комбинированный подход

В зрелых системах часто сначала делят по бизнес-области, а внутри — по технической роли:

```text
analytics/
├── api/
├── application/
├── domain/
└── infrastructure/

reports/
├── api/
├── application/
├── domain/
└── infrastructure/
```

Упрощённо:

```text
Domain first
↓
Technical separation inside
```

## SoC и база данных

Плохо:

```text
Analytics
↓
SQL напрямую

Reports
↓
SQL напрямую

Notifications
↓
SQL напрямую
```

Каждая часть начинает знать внутреннюю схему хранения.

Лучше отделить доступ к данным:

```text
Analytics
↓
AnalyticsRepository
↓
Database
```

Теперь бизнес-логика говорит:

> Дай данные сайта за 30 дней.

А не:

> Выполни конкретный SELECT.

Это отделяет:

```text
Что нужно бизнес-логике
```

от:

```text
Как именно это получить из хранилища
```

## Не превращать SoC в религию

Принцип должен уменьшать сложность, а не увеличивать её.

Не нужно для простейшей операции автоматически создавать:

```text
UserController
UserApplicationService
UserDomainService
UserRepositoryInterface
PostgresUserRepository
UserMapper
UserDTO
```

если задача этого не требует.

Это снова trade-off.

## Связь с Cohesion и Coupling

```text
Separation of Concerns
↓
правильные границы
↓
High Cohesion
+
Lower Coupling
```

Если Analytics занимается только аналитикой — cohesion выше.

Если Telegram вынесен из Analytics — ненужный coupling ниже.

## Связь с Single Responsibility

SoC — широкий принцип разделения разных concerns.

**Single Responsibility Principle** конкретнее: у части системы должна быть основная причина для изменения.

Например, Report Generator должен меняться из-за логики формирования отчёта, а не из-за изменений Telegram API или формулы CTR.

## SoC и AI

Плохой вариант:

```text
AI Module
├── получает данные
├── рассчитывает показатели
├── определяет проблемы
├── генерирует текст
└── отправляет Telegram
```

Хорошее разделение:

```text
Collector
↓
Analytics
↓
Rules
↓
AI Advisor
↓
Report
```

AI отвечает только за задачи, где полезна вероятностная модель:

- объяснение;
- гипотезы;
- приоритизация;
- рекомендации.

## Authentication и Authorization как разные concerns

```text
Authentication
→ кто ты?
```

```text
Authorization
→ что тебе разрешено?
```

Это разные ответственности, даже если в маленьком проекте они физически находятся рядом.

## Как искать concerns

В описании системы полезно искать глаголы:

```text
получать
нормализовать
хранить
считать
проверять
объяснять
формировать
уведомлять
авторизовывать
```

Это потенциальные области ответственности.

Но:

```text
1 глагол ≠ автоматически 1 сервис
```

Глаголы помогают увидеть границы, а не диктуют deployment.

## Что запомнить

- разные виды ответственности нужно разделять;
- SoC — причина разделения, а модули/слои/сервисы — способы его реализовать;
- можно разделять горизонтально и вертикально;
- для модульного монолита часто удобно сначала делить по бизнес-области;
- чрезмерное дробление тоже создаёт сложность.

# 1.5 — Encapsulation и Information Hiding

## Цель темы

Понять, почему после разделения системы важно скрывать внутреннюю реализацию модулей и давать другим частям только необходимый публичный интерфейс.

## Encapsulation

**Encapsulation** — сокрытие внутренней реализации компонента за понятным интерфейсом.

Плохо:

```text
Report
↓
читает внутренние таблицы Analytics
↓
знает внутренние поля
↓
вызывает внутренние функции
```

Лучше:

```text
Report
↓
Analytics API / Contract
↓
Analytics
```

Report знает только публичную операцию и формат результата.

Например:

```text
get_analysis_result(site_id)
```

возвращает:

```json
{
  "ctr": 1.4,
  "traffic_change": -22,
  "avg_position": 8.2
}
```

Report не обязан знать:

- из каких таблиц пришли данные;
- какие функции вызвались;
- используется ли кэш;
- какой алгоритм расчёта работает внутри.

## Information Hiding

**Information Hiding** — идея скрывать внутренние решения, которые могут измениться, от частей системы, которым эти детали не нужны.

Например, внутри Collector можно заменить HTTP-библиотеку:

```text
requests
↓
httpx
```

Если Analytics и Reports ничего не заметили, граница хорошая.

## Public API и Internal Implementation

Полезно мысленно разделять:

```text
PUBLIC
```

и:

```text
PRIVATE / INTERNAL
```

Например:

```text
analytics/
├── public:
│   └── analyze_site()
│
└── internal:
    ├── calculate_ctr()
    ├── aggregate_positions()
    ├── normalize_period()
    └── load_internal_config()
```

Другим модулям желательно пользоваться `analyze_site()`, а не случайными внутренними функциями.

## Почему это уменьшает coupling

Без инкапсуляции:

```text
A
↓
знает много деталей B
```

С инкапсуляцией:

```text
A
↓
знает только публичный контракт B
```

Чем меньше внутренних знаний распространяется по системе, тем легче менять реализацию.

## Encapsulation — не только private-методы

Инкапсуляция — архитектурная идея.

Она существует и между сервисами:

```text
Report Service
↓ HTTP API
Analytics Service
```

Report не видит внутренний код Analytics вообще.

## Пример на SEO-платформе

```text
Collector
→ collect(site_id)

Analytics
→ analyze(dataset)

Rules
→ evaluate(analysis)

Report
→ generate(result)
```

Общий поток:

```text
Collector
↓
Analytics
↓
Rules
↓
Report
```

Каждый модуль раскрывает только необходимый интерфейс.

## Плохой вариант

```text
Report
↓
analytics._calculate_ctr()
↓
analytics._db_connection
↓
analytics.internal_cache
```

Теперь Report зависит от внутренней реализации Analytics.

Любой рефакторинг становится рискованнее.

## Public Surface Area

Полезная идея:

> Чем меньше публичный интерфейс модуля, тем легче контролировать его использование.

Иногда вместо большого набора внутренних операций:

```text
calculate_ctr()
calculate_position()
load_data()
normalize_data()
get_raw_rows()
get_internal_config()
```

другим модулям достаточно:

```text
analyze_site()
```

Это уменьшает **public surface area**.

## Но слишком большой «единый метод» тоже плох

Функция вроде:

```text
analyze_everything_in_the_world()
```

не делает архитектуру хорошей автоматически.

Если внутри смешаны десятки несвязанных обязанностей, нарушается cohesion.

Поэтому Encapsulation работает вместе с:

```text
Separation of Concerns
High Cohesion
Controlled Coupling
```

## Что запомнить

- разделить систему недостаточно — нужно ещё скрыть внутреннюю реализацию;
- другие модули должны знать контракт, а не внутренности;
- публичный интерфейс желательно делать минимальным и понятным;
- Information Hiding защищает систему от каскадных изменений;
- инкапсуляция работает на уровне функций, модулей, компонентов и сервисов.

# 1.6 — Dependency Direction

## Цель темы

Понять, почему важно не только наличие зависимостей, но и их направление.

## Базовая идея

Даже хорошо разделённые компоненты всё равно зависят друг от друга.

Нужно контролировать:

> Кто от кого зависит?

Например:

```text
Rules
↓
PostgreSQL
```

Работать может, но теперь важная бизнес-логика напрямую зависит от конкретной технологии хранения.

## Проблема зависимости от технической детали

Если Rules знает:

- SQL;
- названия таблиц;
- конкретный драйвер PostgreSQL;
- способ подключения;

то смена инфраструктуры может заставить менять бизнес-логику.

Получается:

```text
Business Logic
↓
Infrastructure Detail
```

Сильная архитектура старается уменьшать такую зависимость.

## Зависимость через абстракцию

Более гибкий вариант:

```text
Rules
↓
Data Interface
↑
PostgreSQL Adapter
```

Rules знает только необходимый контракт данных.

PostgreSQL Adapter реализует этот контракт.

Теперь бизнес-правила не обязаны знать, как именно данные физически хранятся.

## Главный принцип

```text
Важная бизнес-логика
не должна без необходимости зависеть
от низкоуровневых технических деталей
```

Например:

```text
Rules
```

выражает бизнес-решения системы.

А:

```text
PostgreSQL driver
```

— техническая деталь реализации.

Желательно строить систему так, чтобы инфраструктура обслуживала бизнес-логику, а не бизнес-логика формировалась вокруг конкретной инфраструктуры.

## Пример на SEO-проекте

Плохо:

```text
Rule Engine
↓
PostgreSQL
↓
конкретная таблица seo_metrics
```

Лучше:

```text
Rule Engine
↓
MetricsRepository Contract
↑
PostgresMetricsRepository
```

Rule Engine может просить:

```text
get_metrics(site_id, period)
```

и не знать, откуда они пришли физически.

## Dependency Direction и внешние API

Та же идея применима к внешним сервисам.

Плохо:

```text
Analytics
↓
жёстко зависит от Yandex API format
```

Лучше:

```text
Yandex API
↓
Yandex Adapter
↓
Internal Data Contract
↓
Analytics
```

Теперь внешний формат находится на краю системы.

Это снова принцип:

> Isolate what you don't control.

## Dependency Direction и AI

Плохо:

```text
Rules
↓
LLM
```

если Rules без AI не может определить объективную проблему.

Лучше:

```text
Analytics
↓
Rules
↓
Problem Result
↓
AI Advisor
```

Тогда детерминированное ядро не зависит от вероятностной внешней системы.

## Связь с Dependency Inversion

Эта тема напрямую подводит к **Dependency Inversion Principle**.

Упрощённая идея:

```text
High-level policy
↓
Abstraction
↑
Low-level implementation
```

То есть верхнеуровневая бизнес-логика зависит от абстрактного контракта, а конкретная техническая реализация подстраивается под него.

Полностью Dependency Inversion будет разобран вместе с SOLID.

## Направление runtime-вызова и направление зависимости — не всегда одно и то же

Это важное уточнение.

Фактически в runtime PostgreSQL ничего не «вызывает» в Rules.

Но на уровне исходного кода может быть устроено так, что:

```text
Rules imports psycopg
```

и тогда Rules зависит от PostgreSQL-драйвера.

То есть важно различать:

- **runtime interaction** — кто кого вызывает при работе системы;
- **source-code dependency** — какой код должен знать о каком коде/контракте.

Архитектор контролирует оба аспекта.

## Не делать правило абсолютным

Dependency Direction — не означает, что любая зависимость от framework или базы запрещена.

Для маленькой системы прямой доступ может быть оправдан.

Нужно спрашивать:

> Эта зависимость создаёт реальный риск изменений или лишнюю связанность?

Если нет — дополнительная абстракция может быть лишней.

## Итоговая связка тем 1.4–1.6

```text
Separation of Concerns
↓
разделяем разные ответственности

Encapsulation
↓
скрываем внутреннюю реализацию каждой части

Dependency Direction
↓
контролируем, кто от кого зависит
```

Вместе с предыдущими темами:

```text
High Cohesion
+
Controlled Coupling
+
Separation of Concerns
+
Encapsulation
+
Intentional Dependency Direction
```

это уже фундамент для проектирования устойчивого модульного монолита.

## Что запомнить

1. Разные concerns нужно отделять друг от друга.
2. Модули должны скрывать внутренние детали за контрактами.
3. Публичный интерфейс должен быть минимально достаточным.
4. Важная бизнес-логика не должна без необходимости зависеть от инфраструктурных деталей.
5. Внешние API и LLM желательно держать на краях системы.
6. Абстракции создаются не ради красоты, а чтобы контролировать реальные зависимости.
7. Следующий логичный шаг — Dependency Inversion и SOLID.
