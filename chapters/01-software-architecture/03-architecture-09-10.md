## Темы 0.9–0.10

# 0.9 Компонент, модуль, слой, сервис и микросервис

## Цель темы
Разделить термины, которые часто ошибочно используют как синонимы.

## Компонент
**Компонент** — логически самостоятельная часть системы с определённой ответственностью.

Главный вопрос:

> За что отвечает эта часть системы?

Примеры:

```text
Analytics
Rule Engine
Report Generator
Authentication
Notifications
```

Компонент не обязан быть:
- папкой;
- контейнером;
- сервером;
- отдельным процессом.

Он описывает прежде всего ответственность.

## Модуль
**Модуль** — способ организовать код вокруг определённой области ответственности.

Пример:

```text
analytics/
├── ctr.py
├── traffic.py
├── positions.py
└── conversions.py
```

Компонент `Analytics` может быть реализован одним модулем или несколькими.

## Компонент и модуль

Простой проект:

```text
Компонент:
Analytics

Реализация:
analytics/
```

Большой проект:

```text
Компонент:
Analytics

Модули:
analytics/traffic/
analytics/positions/
analytics/keywords/
analytics/competitors/
```

Компонент — логическая сущность.
Модуль — организация кода.

## Слой — Layer
**Слой** — уровень системы, объединяющий код по типу ответственности.

Классическая модель:

```text
Presentation Layer
↓
Business Layer
↓
Data Layer
```

### Presentation Layer
Отвечает за взаимодействие с внешним пользователем или клиентом:
- web UI;
- API controllers;
- формы;
- представление результата.

### Business Layer
Содержит бизнес-логику:
- правила;
- аналитику;
- проверки;
- принятие решений.

### Data Layer
Работает с хранением и получением данных:
- SQL;
- ORM;
- базы данных;
- файловые хранилища;
- репозитории.

## Компонент и слой

`Analytics` может быть компонентом внутри `Business Layer`.

```text
Business Layer
├── Analytics
├── Rules
└── Reports
```

То есть:

```text
Layer = уровень
Component = ответственность
```

## Сервис
Термин **service** перегружен и может означать разные вещи.

В архитектуре приложения полезно понимать сервис как часть системы, которая предоставляет определённую операцию или набор возможностей через понятный интерфейс.

Примеры:

```text
Notification Service
Authentication Service
Analytics Service
```

Сервис может быть:
- классом;
- модулем;
- частью монолита;
- отдельным процессом.

Поэтому слово `service` само по себе ещё не означает микросервис.

## Микросервис
**Микросервис** — автономно развёртываемый сервис с собственной границей ответственности, взаимодействующий с другими частями системы через сетевой контракт.

Ключевые свойства:
- независимый deployment;
- отдельный процесс;
- сетевое взаимодействие;
- собственный жизненный цикл;
- чёткая ответственность.

Пример:

```text
Backend API
↓ HTTP
Analytics Service
```

или:

```text
API Gateway
├── Auth Service
├── Analytics Service
├── Notification Service
└── Report Service
```

## Важное уточнение

```text
Docker Container ≠ автоматически Microservice
```

Для микросервиса важны:
- автономность;
- независимое развёртывание;
- граница ответственности;
- сетевой контракт.

## Что меняется при выносе Analytics в отдельный сервис

До:

```text
Backend
└── analytics/
```

После:

```text
Backend
↓ HTTP
Analytics Service
```

Бизнес-смысл Analytics желательно сохранить.

Контракт данных тоже желательно сохранить.

Но появляется эксплуатационная сложность:
- сетевой вызов;
- timeout;
- retry;
- отдельные логи;
- недоступность сервиса;
- отдельный deployment;
- возможная межсервисная авторизация;
- healthcheck;
- мониторинг.

## Timeout
**Timeout** — ограничение максимального времени ожидания ответа.

Пример:

```text
Backend вызывает Analytics

если ответа нет 5 секунд
→ прекратить ожидание
```

## Retry
**Retry** — повторная попытка выполнить временно неуспешную операцию.

Пример:

```text
Запрос упал из-за временной ошибки
↓
повторить ещё 1–2 раза
```

Retry нельзя использовать бездумно: некоторые операции небезопасно повторять.

## Библиотека
**Библиотека** — переиспользуемый код, предназначенный для использования в разных проектах или частях системы.

Примеры:
- HTTP-клиент;
- библиотека обработки таблиц;
- библиотека логирования.

Библиотека обычно не должна знать бизнес-логику конкретного SEO-проекта.

## Пакет
**Пакет** — механизм организации и поставки кода в конкретной экосистеме.

Например в Python:

```text
analytics/
├── __init__.py
├── ctr.py
└── traffic.py
```

`Package` — прежде всего организационный или языковой термин, а не архитектурная роль.

## Краткая карта терминов

```text
Component
→ логическая ответственность

Module
→ организация кода

Layer
→ архитектурный уровень

Service
→ предоставляемая возможность через интерфейс

Microservice
→ автономно развёртываемый сетевой сервис

Library
→ переиспользуемый код

Package
→ упаковка и организация кода
```

## Типичные ошибки
- считать модуль и микросервис одним и тем же;
- считать каждый Docker-контейнер микросервисом;
- путать слой с компонентом;
- использовать слово service без уточнения;
- выносить сервис отдельно без реальной причины.

## Что нужно запомнить
- термины описывают систему с разных сторон;
- один и тот же Analytics может быть одновременно компонентом, модулем и сервисом;
- микросервис — не просто «папка в Docker»;
- физическое разделение добавляет сетевую и эксплуатационную сложность.

# 0.10 Абстракции и уровни абстракции

## Цель темы
Научиться обсуждать систему на правильном уровне детализации и не смешивать бизнес, архитектуру и реализацию.

## Определение
**Абстракция** — намеренное сокрытие деталей, которые не важны для текущего вопроса.

Это не потеря информации.

Это выбор подходящего уровня детализации.

## Пример с картой

```text
Земля
↓
Европа
↓
Германия
↓
Город
↓
Улица
↓
Дом
↓
Квартира
```

Каждый уровень описывает одну и ту же реальность, но с разной детализацией.

## SEO-платформа на разных уровнях

### Уровень 1

```text
SEO Intelligence Platform
```

### Уровень 2

```text
Collector
Analytics
Rules
Reports
AI
```

### Уровень 3

```text
Collectors
├── Yandex
├── Google
└── Ahrefs
```

### Уровень 4

```text
Yandex Collector
├── HTTP
├── OAuth
├── JSON
├── Retry
└── Timeout
```

### Уровень 5

```python
response.json()["metrics"][0]["clicks"]
```

Все уровни правильные.

Они просто отвечают на разные вопросы.

## Лестница абстракций

```text
Бизнес
↓
Продукт
↓
Архитектура
↓
Компоненты
↓
Модули
↓
Классы
↓
Функции
↓
Код
```

## Бизнес-уровень
Главный вопрос:

> Зачем существует продукт?

Пример:

```text
Автоматизировать SEO-аналитику
и снизить объём ручной работы
```

## Продуктовый уровень
Главный вопрос:

> Что получает пользователь?

Пример:

```text
Автоматический анализ
+ список проблем
+ рекомендации
```

## Архитектурный уровень
Главный вопрос:

> Из каких крупных частей состоит система?

```text
Collector
Analytics
Rules
Reports
AI
```

## Уровень компонента
Главный вопрос:

> За что отвечает конкретная часть?

```text
Analytics
→ рассчитывает показатели
```

## Уровень модулей
Главный вопрос:

> Как внутренне организована ответственность?

```text
analytics/
├── ctr
├── traffic
├── positions
└── conversions
```

## Уровень реализации
Главный вопрос:

> Каким конкретным кодом это реализовано?

Например:

```python
ctr = clicks / impressions * 100
```

## Типичная ошибка новичка
На вопрос:

> Что строим?

ответить:

```text
FastAPI + PostgreSQL + Redis
```

Это технологии.

Они не объясняют продукт.

Правильная последовательность:

```text
Проблема
↓
Продукт
↓
Архитектура
↓
Компоненты
↓
Технологии
↓
Код
```

## Почему это важно для работы с ИИ

Плохой запрос:

```text
Сделай FastAPI приложение.
```

ИИ не знает:
- что это за продукт;
- где границы;
- какие ответственности;
- какие ограничения.

Лучший запрос:

```text
Мы строим платформу SEO-аналитики.

Логические компоненты:
- Collector
- Analytics
- Rule Engine
- Reports

Collector должен быть расширяемым.
Rules не должны зависеть от AI.

Backend реализуем на FastAPI.
```

Сначала задаётся архитектурная модель.

Потом технология.

## Правило

> Не отвечай на вопрос другого уровня абстракции.

Если вопрос:

```text
Что делает Collector?
```

ответ:

```text
Получает данные из внешних источников.
```

А не:

```text
Использует requests и asyncio.
```

Потому что технологии — более низкий уровень.

## Тест глагола для компонентов
Хороший компонент можно описать глаголом.

```text
Collector
→ собирает

Analytics
→ рассчитывает

Rules
→ проверяет

Reports
→ формирует

Notifications
→ уведомляет
```

Если объект сложно описать действием, возможно, он:
- не является компонентом;
- слишком большой;
- слишком абстрактный.

## Пример YouTube

Площадка для распространения видео и монетизации внимания и контента.

### Продукт
Пользователь получает:
- поиск;
- просмотр видео;
- рекомендации;
- подписки;
- плейлисты;
- публикацию собственного контента.

## Типичные ошибки
- смешивать бизнес-цели и технические компоненты;
- называть технологию вместо архитектурной ответственности;
- слишком рано уходить в детали;
- обсуждать реализацию до определения границ;
- считать один уровень описания «более правильным», чем другой.

## Что нужно запомнить
- абстракция позволяет управлять сложностью;
- разные уровни описания одной системы одновременно верны;
- архитектор умеет переключаться между уровнями;
- сначала определяй проблему и архитектуру, потом технологии;
- при работе с ИИ особенно важно явно задавать уровень задачи.
